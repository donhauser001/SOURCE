## 一、需求理解与边界约束

### 1.1 需求目标（Goals）

**用户最终能完成什么？**
- 管理员可以完整管理用户生命周期（包括禁用/删除）
- 管理员可以为其他用户生成 API 密钥
- 系统管理员可以配置站点级参数
- 大数据量导入不会阻塞 UI

**系统层面打通哪条闭环？**
```
后台管理完整闭环：
创建 → 编辑 → 批量操作 → 禁用/删除 → 审计追踪
```

**MVP 成功定义：**
- P1 任务全部完成
- 管理员可进行所有基础 CRUD 操作
- 所有敏感操作有审计日志

### 1.2 非目标（Non-Goals）

| 内容 | 原因 | 延后到 |
|------|------|--------|
| 微信小程序开发 | 独立项目，需单独规划 | MP 1.0 |
| Redis 缓存 | 当前数据量不需要 | P3/可选 |
| 虚拟滚动 | 分页已解决主要问题 | P3/可选 |
| 代码重构（表格/筛选组件） | 功能优先，后续优化 | v1.1 |

### 1.3 约束条件（Constraints）

**技术栈约束：**
- tRPC + Prisma 架构
- 所有管理员操作需记录 `AdminAuditLog`
- 软删除优先于硬删除

**规范约束：**
- 用户删除使用"禁用"而非物理删除（数据保留）
- API 密钥删除后不可恢复

### 1.4 风险前置（Key Risks）

| 风险类型 | 风险描述 | 缓解措施 |
|---------|---------|---------|
| 数据风险 | 用户删除可能影响关联数据 | 实现软删除（禁用状态） |
| 安全风险 | 管理员密钥生成可能被滥用 | 记录完整审计日志 |
| 性能风险 | 异步队列引入新依赖 | 评估是否使用 inngest |

### T1.1 用户禁用/删除功能

**【任务名称】**  
为 User 模型添加禁用/删除能力，管理员可管理用户完整生命周期

**【级别】** P1

**【产出物（Deliverables）】**
- 修改 `/apps/web/prisma/schema.prisma` - 添加 `isActive` 字段
- 修改 `/apps/web/src/server/routers/user.ts` - 添加 `adminDisable` 和 `adminDelete`
- 修改 `/apps/web/src/app/admin/users/page.tsx` - 添加操作按钮

**【涉及范围（Scope）】**
- 涉及：User 模型、user router、用户管理页面
- 不涉及：登录流程（禁用用户登录时自动拒绝）

**【依赖关系（Dependencies）】**
- 前置任务：无
- 外部依赖：无

**【测试点（Test Points）】**
- 禁用用户后，该用户无法登录
- 禁用用户后，其 API 密钥自动失效
- 删除用户前检查是否有关联数据
- 审计日志正确记录操作

**【验收标准（Acceptance Criteria）】**
- User 模型新增 `isActive Boolean @default(true)` 字段
- `adminDisable` procedure：设置 `isActive = false`
- `adminDelete` procedure：检查关联数据，无关联则物理删除
- 所有操作调用 `logAdminAction`

**【风险与回滚（Risk & Rollback）】**
- 风险：中 - 数据库 schema 变更
- 回滚：`prisma migrate rollback`
